# MSDS JSON 라벨링 규칙

## 1. 적용 범위와 원칙

MSDS 원문에서 제품 식별, 권고 용도, 사용 제한, 공급자, 구성성분, GHS 분류, 신호어, 유해·위험 문구를 추출할 때 사용한다. 원문에 없는 사실을 화학 지식이나 다른 제품의 자료로 채우지 않는다. 법적 분류의 타당성을 판정하는 규칙이 아니라 **기존 라벨의 일관성을 유지하기 위한 데이터 입력 규칙**이다.

- 제품별 JSON 파일 하나를 만든다. 파일명은 해당 데이터셋의 제품 ID를 사용한다(예: `KR-OCI-003.json`). 
- 아래 9개 최상위 키를 모두 유지한다. 값이 없어도 키를 생략하지 않는다.
- 원문의 문자열은 가능한 한 그대로 전사한다. 특히 물질명, CAS/KE 번호, 함량 범위, 주소, 전화번호, H 문구는 임의 번역·보정·계산하지 않는다.
- 서로 다른 버전의 MSDS나 비슷한 제품의 값을 합치지 않는다. 같은 제조사 제품도 개별 문서로 판정한다.

## 2. JSON 구조

| 최상위 필드 | 형식 | 하위 필드 |
|---|---|---|
| `product_name` | 객체 | `value`, `source_status` |
| `recommended_use` | 객체 | `value`, `source_status` |
| `use_restrictions` | 객체 | `value`, `source_status` |
| `supplier` | 객체 | `company_name`, `address`, `emergency_phone` |
| `ingredients` | 배열 | 각 항목: `chemical_name`, `cas_number`, `ke_number`, `content`, `is_substitute_data` |
| `ghs_classification` | 배열 | 각 항목: `hazard_class`, `category` |
| `signal_word` | 객체 | `value`, `source_status` |
| `hazard_statements` | 배열 | 각 항목: `code`, `text` |
| `list_status` | 객체 | `ingredients`, `ghs_classification`, `hazard_statements` |

### 상태값

단일값 객체의 `source_status`와 배열의 `list_status`에는 `기재`, `자료없음`, `해당없음` 중 해당하는 값을 사용한다.

| 상태 | 판정 기준 | JSON 표현 |
|---|---|---|
| `기재` | 대상 정보가 원문에 확인됨 | 단일값은 문자열, 배열은 하나 이상의 항목 |
| `자료없음` | 확인한 원문에서 대상 정보를 얻지 못함 | 단일값은 `null`, 배열은 `[]` |
| `해당없음` | 원문이 명시적으로 비대상·없음으로 표시하거나 해당 항목이 적용되지 않음을 확인함 | 단일값은 `null`, 배열은 `[]` |

빈칸만 보고 `해당없음`으로 추정하지 않는다. 상태의 근거를 원문에서 확인할 수 없다면 `자료없음`을 사용한다. 현재 43개에서는 `기재`인 단일값에 `null`이 없고, `기재`인 배열에 빈 배열이 없다.

## 3. 필드별 라벨링

### 3.1 제품·용도·사용 제한

1. `product_name.value`: 제품 식별명 전체를 기재한다. 괄호, 상표, 영문 병기, 이전 명칭이 원문 이름에 들어 있다면 유지한다.
2. `recommended_use.value`: 권고 용도 또는 권장 사용처를 문자열로 기재한다. 번호나 복수 용도가 한 문구에 함께 있으면 원문 표현을 유지한다.
3. `use_restrictions.value`: 사용상의 제한 문구를 기재한다. 권고 용도만으로 제한사항을 새로 만들어 내지 않는다.
4. 세 필드의 `source_status`는 각 필드별로 독립 판정한다. 제품명이 기재되어 있어도 사용 제한이 비어 있을 수 있다.

### 3.2 공급자

- `supplier.company_name`: 공급자/제조사 이름을 문서에 적힌 대로 기록한다.
- `supplier.address`: 문서의 해당 주소를 문자열로 기록한다.
- `supplier.emergency_phone`: 긴급 연락처를 문자열로 기록한다. 국가번호, 하이픈, 괄호, 문자 접두어를 제거하지 않는다.
- 확인되지 않은 하위값만 `null`로 둔다. `supplier` 객체는 항상 유지한다. 전화번호를 일반 대표전화로 대체하거나 다른 제품에서 복사하지 않는다.

### 3.3 구성성분 `ingredients`

원문 성분 표의 각 행을 하나의 객체로 기록하고 표시 순서를 유지한다.

| 필드 | 입력 기준 |
|---|---|
| `chemical_name` | 원문의 화학물질명 또는 대체 명칭. 영업비밀 표기도 그대로 기록 |
| `cas_number` | 확인된 CAS 번호 문자열. 없으면 `null` |
| `ke_number` | 확인된 KE 번호 문자열. 없으면 `null` |
| `content` | 함유량·범위의 원문 문자열. `24~26`, `53∼63`, `90-100` 등 기호와 자릿수를 임의 통일하지 않음 |
| `is_substitute_data` | `영업비밀`, `S1(영업비밀)`처럼 대체자료로 명시된 행이면 `true`, 그렇지 않으면 `false` |

함량의 단위와 기준을 원문 밖에서 추정하지 않는다. 범위의 중간값 계산, 합계 100으로의 보정, CAS 번호 역추정은 하지 않는다. 성분 목록이 비면 `[]`로 두고 `list_status.ingredients`를 판정한다.

### 3.4 GHS 분류 `ghs_classification`

원문에 제시된 각 유해성 분류를 한 객체로 기록하고 표시 순서를 유지한다.

- `hazard_class`: 유해성 종류. 원문 분류명을 그대로 기록한다. 노출 경로·매체가 **분류명 안에** 적혀 있으면 보존한다(예: `급성 독성(흡입: 증기)`). 서로 다른 노출 경로를 하나로 합치지 않는다.
- `category`: 숫자 등급은 **`구분 N` 또는 `구분 N대문자`** 형식으로 기록한다. 예: `3`·`구분3` → `구분 3`, `1A` → `구분 1A`, `2a` → `구분 2A`.
- 등급 뒤 괄호 설명은 `category`에서 제거한다. 예: `구분 1(1A/1B/1C)` → `구분 1`, `구분 3(호흡기계 자극)` → `구분 3`, `4(증기)` → `구분 4`. 등급 뒤에 붙은 노출 매체 부기(원문 `흡입4(증기)`의 `(증기)`)도 제거하며, `hazard_class`로 옮기지 않는다(예: `KR-NOROO-002` · `KR-NOROO-005` → `급성독성물질 흡입` + `구분 4`).

- 숫자 등급이 아닌 범주(`액화가스`)는 그대로 기록한다. 원문에서 등급을 확인할 수 없는 분류의 `category`는 `null`로 둔다. 숫자를 임의 부여하지 않는다.
- 같은 `hazard_class`가 여러 항목에 반복되어도 등급·노출 경로가 다르면 각각 유지한다.

현재 43개의 GHS 분류 133건 중 숫자 등급 131건은 위 형식이며, 예외는 `액화가스` 1건(`KR-OCI-005`)과 `null` 1건(`KR-NEOGEN-002`)이다. `hazard_class`의 철자나 띄어쓰기는 별도 표준화 범위를 정하지 않은 한 임의로 바꾸지 않는다.

### 3.5 신호어·유해위험 문구

- `signal_word.value`: 원문 신호어(`위험`, `경고`)를 기록한다. 확인되지 않거나 해당되지 않으면 `null`로 두고 `source_status`를 각각 판정한다. GHS 등급만 보고 신호어를 생성하지 않는다.
- `hazard_statements`: 문구 하나마다 `{ "code": ..., "text": ... }` 객체를 만들고 원문 순서를 유지한다.
- `text`: 유해·위험 문구를 원문대로 기록한다. `code`: 같은 항목에서 H 코드가 명시되고 판독 가능할 때만 문자열로 기록한다. 문구만 있거나 코드가 불명확하면 `null`이다.
- 알려진 문구와 비슷하다는 이유로 H 코드를 자동 매칭하지 않는다. 유해성 분류에서 문구를 역생성하지 않는다. 배열이 비면 `list_status.hazard_statements`를 독립 판정한다.

## 4. 검수 규칙

1. 모든 파일이 유효한 UTF-8 JSON이고 최상위 키 9개 및 하위 키가 구조표와 일치하는지 확인한다.
2. `source_status`가 `기재`이면 `value`가 문자열이고, `자료없음`·`해당없음`이면 `value`가 `null`인지 확인한다.
3. `list_status`가 `기재`이면 해당 배열이 비어 있지 않고, 나머지 두 상태라면 빈 배열인지 확인한다.
4. 성분마다 `is_substitute_data`가 JSON 불리언인지 확인한다. CAS/KE 번호와 H 코드는 문자열 또는 `null`로 유지한다.
5. 숫자형 `category`에 `^(구분 [0-9]+[A-Z]?)$`가 적용되는지 확인한다. `액화가스` 및 근거 없는 `null`은 숫자 등급으로 강제하지 않는다.
6. 원문과 대조해 제품명·성분 함량·긴급전화·H 문구의 숫자 및 기호를 확인한다. 특히 비슷한 제품 간 값을 복사하지 않았는지 검수한다.
7. 수정 시 원본과 비교해 바뀐 필드의 경로와 이전/이후 값을 기록한다. 의미 있는 항목 추가·삭제를 배열 이동과 구별한다.

## 5. 범위의 한계

이 문서는 43개 JSON의 공통 구조와 이미 적용된 정규화 방식을 재현한다. 실제 MSDS 원문과의 정확성, 최신 규제 적합성, GHS 분류의 과학적 타당성은 이 JSON만으로 확정할 수 없으므로 원문 및 담당자 검수가 필요하다.
