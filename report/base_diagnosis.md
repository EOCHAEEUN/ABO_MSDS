# Base 모델 진단 — "val이 너무 쉬웠다"

> 작성 2026-09-26 · 모델 Qwen3-4B (4bit NF4, greedy, thinking 끔) · 프롬프트 `core/prompt.py` · few-shot `KR-HANIL-002` + `KR-KUMHO-002`

## 한 줄 요약

**기존 val 4건에서 Base few-shot이 GHS·H코드·스키마 만점을 냈다. 그런데 다른 서식의 문서에서는 H코드를 지어내고 분류명을 잘못 읽는다.**
val을 다시 짜서(수입품 2건 추가) 이 약점이 점수에 드러나게 했다.

---

## 1. 무엇이 문제였나

QLoRA의 효과는 **Base와 비교해서** 보여줘야 한다. 그런데 기존 val 4건으로 잰 Base 점수가 이랬다.

| 지표 | base_zs | base_fs |
|---|---|---|
| 스키마 준수율 | 0.25 | **1.00** |
| GHS F1 | 0.00 | **1.00** |
| H코드 F1 | 1.00 | **1.00** |
| CAS F1 | 0.96 | 0.92 |

few-shot만으로 거의 만점이라 **QLoRA가 val에서 더 나아질 여지가 없었다.** 이대로면 r1과 r2도 비교할 수 없었다.

원인은 val 구성에 있었다.
- 4건 모두 **현행 서식 국문**이었다.
- 그중 2건(GSC)은 분류가 "해당없음"인 윤활유라 GHS·H코드 채점에서 빠진다.
- 그래서 **GHS·H코드 점수가 문서 2건, 항목 10개로만** 계산됐다.

## 2. 어떻게 확인했나

Base 모델을 **train 문서**에 돌려서 난이도 분포를 봤다.
- Base는 학습하지 않은 상태라 train 문서도 처음 보는 문서다.
- 봉인된 test는 쓰지 않았다.
- few-shot 예시 2건은 제외했다(정답을 보고 푸는 셈이라).
- 이 점수는 **진단용**이라 `report/scores.csv`에 기록하지 않았다.

## 3. 결과: 서식이 바뀌면 Base가 무너진다

| 지표 | 기존 val (4건) zs / fs | **train 진단 (20건)** zs / fs | **새 val (6건)** zs / fs |
|---|---|---|---|
| 스키마 준수율 | 0.25 / 1.00 | 0.55 / 0.90 | 0.50 / 1.00 |
| 제품명 | 0.75 / 1.00 | 0.95 / 0.85 | 0.83 / 1.00 |
| 분류 목록 상태 | 1.00 / 1.00 | 0.75 / 0.90 | 1.00 / 1.00 |
| **GHS F1** | 0.00 / **1.00** | 0.66 / **0.83** | 0.11 / **0.75** |
| H코드 정밀도 | 1.00 / 1.00 | 0.83 / **0.84** | 1.00 / 1.00 |
| **H코드 없는 문구 F1** | (해당 문서 없음) | **0.00 / 0.00** | (해당 문서 없음) |
| CAS F1 | 0.96 / 0.92 | 0.96 / 0.99 | 0.98 / 0.95 |

- **성분표(CAS·함유량)는 어디서나 잘 읽는다.** Base의 강점이다.
- **분류(GHS)와 H코드는 서식이 바뀌면 크게 떨어진다.** 기존 val은 이 약점을 가리고 있었다.

## 4. Base가 틀리는 다섯 가지 유형

### ① H코드를 지어낸다: 가장 심각
`KR-NOROO-005`(구서식)는 원문에 H코드가 없다.

```
원문   3) 유해·위험문구 : 고인화성 액체 또는 증기 ▷피부와 접촉하면 유독함 ▷흡입하면 유독함 ▷흡입하면 유해함 ...
정답   {"code": null, "text": "피부와 접촉하면 유독함"}
Base   {"code": "H302", "text": "피부와 접촉하면 유독함"}   ← H302는 "삼키면 유해함"
```
- zero-shot과 few-shot 모두 **13개 문구 전부에 H코드를 만들어 붙였고, 코드와 문구 짝도 틀렸다.**
- 시스템 프롬프트에 "원문에 H코드가 없으면 추정하지 말 것"이라고 적어 뒀는데도 그렇다.
- 안전 문서에서 **없는 코드를 지어내는 것**은 누락보다 위험하다.

### ② 수입품 서식에서 상위 제목을 분류명으로 읽는다
`KR-ITW-001`(수입품 국문판)은 분류 앞에 "물리적 위험성 / 건강 유해성 / 환경 유해성" 같은 묶음 제목이 붙어 있다.

```
원문   물리적 위험성 인화성 액체 구분 2
       건강 유해성 피부 부식성/자극성 구분 2
정답   {"hazard_class": "인화성 액체", "category": "구분 2"}
Base   {"hazard_class": "물리적 위험성", "category": "구분 2"}
```

### ③ 구서식의 분류 표기를 나누지 못한다
```
원문   ▷급성독성물질 경피3 ▷급성독성물질 흡입3(증기)
정답   {"hazard_class": "급성독성물질 경피", "category": "구분 3"}
Base   {"hazard_class": "급성독성물질 경피3", "category": "구분 3"}   ← 숫자가 분류명에 남음
```

### ④ 분류가 없는 문서에서 분류를 지어낸다
`KR-HANIL-001`은 GHS 분류가 "자료없음"이라 정답이 빈 목록 `[]`이다. few-shot Base는 2항의 소제목을 분류로 냈다.
```
원문   ◦ 긴급한 위험 ・유해성 정보 : 피부, 눈에 자극을 야기할 수 있음.
Base   [{"hazard_class": "긴급한 위험 ・유해성 정보"}, {"hazard_class": "눈에 대한 영향"}, ... 6개]
```

### ⑤ 긴 제품명 목록을 포기한다
`KR-KUMHO-004·005`는 제품명이 `PPG 450, PPG 1000, PPG 2070, …`처럼 여러 줄에 걸친 목록이다. few-shot Base는 `"자료없음"`으로 답했다.

## 5. 결정한 것

| 결정 | 내용 |
|---|---|
| **val 재구성** | ITW 그룹(수입품 국문판 2건)을 train에서 val로 옮김. val 4건 → 6건, train 24건 → 22건. 제조사 단위 배정과 val·train 제조사 불겹침 규칙은 유지 |
| **제품명 채점 규칙** | 정답에는 원문 괄호를 남기고, **채점할 때만** 괄호 부기·쉼표·공백을 빼고 비교 (`core/normalize.py`). 예: `신.구콘크리트접착제(경화제)` = `신.구콘크리트접착제` |
| **few-shot 예시** | `KR-HANIL-002`(수기 셋으로 검증, 괄호 부기 제거 예시) + `KR-KUMHO-002`(해당없음 예시). test 제조사(노루)는 제외 |

재구성 뒤 새 val에서 **base_fs의 GHS F1이 0.75**로 내려가, QLoRA가 개선할 여지가 생겼다.

## 6. QLoRA에 주는 의미

- 학습 데이터(`data/train.jsonl`, 179개 예시)는 위 약점을 직접 겨냥한다.
  - **H코드 없는 문구 예시 31개**: 원문에서 H코드를 지운 변형을 만들고, 정답의 `code`도 null로 바꿨다(①)
  - **영업비밀 성분 예시 51개**
- 발표 메시지 후보:
  1. "Base는 형식은 잘 따라 하지만, **원문에 없는 H코드를 지어낸다.** QLoRA의 1차 목표는 지어내지 않게 하는 것이다."
  2. "few-shot은 입력이 2.2배 길다(평균 4,300토큰 대 1,950토큰). QLoRA는 **예시 없이** 같은 수준에 도달해야 의미가 있다."

## 7. 해석할 때 주의할 점

- **train 진단 점수는 보고용 성능이 아니다.** 나중에 QLoRA가 이 문서들로 학습하므로 비교에 쓸 수 없다. 이 문서에서는 **실패 유형(정성)** 근거로만 쓴다.
- 문서 수가 적다(val 6건, 진단 20건). 소수점 차이보다 **유형**을 봐야 한다.
- H코드 없는 문서(구서식)는 train(NOROO-005, HANIL-003)과 test에만 있고 val에는 없다. 노루 그룹이 test 예외 규칙에 묶여 옮기지 못했다. **①번 유형의 개선은 test에서 처음 확인하게 된다.**

## 재현

```bash
venv/bin/python eval/infer.py --condition base_fs --split val      # 추론 (base_zs도 동일)
venv/bin/python eval/score.py --condition base_fs --split val      # 채점 → report/scores.csv
venv/bin/python eval/infer.py --condition base_fs --split train    # 진단 (few-shot 예시 자동 제외)
venv/bin/python eval/score.py --condition base_fs --split train    # scores.csv에 쓰지 않음
```
문서별 상세: `outputs/{조건}/{split}/_score_detail.json`
