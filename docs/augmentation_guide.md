# 데이터 증강 유의사항 (파일럿 프리셋 기준)

> 데이터 · 학습 담당용입니다. 규칙의 근거는 [`docs/plan.md`](plan.md) 2절(출력 규칙) · 3.2절(분할) · 3.4절(증강) · 6절(최대 길이)과 [`CLAUDE.md`](../CLAUDE.md)입니다.
> 수치는 파일럿(`feat/web`) 기록입니다. 재시작의 근거로 쓰지 않고, 규모를 짐작하는 참고로만 씁니다.

## 0. 프리셋이 무엇이고 어디에 있나

"프리셋"은 파일럿에서 쓴 증강 구성입니다. **`feat/web` 브랜치에만 있고, main의 같은 파일은 빈 틀입니다.**

| 파일 | 하는 일 |
|---|---|
| `pipeline/augment/renderers.py` | 렌더러 5종. 라벨은 그대로 두고 겉모양만 바꿈 |
| `pipeline/augment/mutators.py` | 내용 변형 3종. 텍스트와 라벨을 함께 바꿈 |
| `pipeline/augment/check_forbidden.py` | 변형 뒤에 정답 값이 사라지지 않았는지 검사 |
| `pipeline/build_jsonl.py` | 위 셋을 묶어 `train.jsonl` · `val.jsonl` 생성 |

- **읽기만 할 때:** `git show feat/web:pipeline/augment/renderers.py`
- **가져올 때:** main에서 만든 작업 브랜치에서 `git checkout feat/web -- <파일>`로 가져오고, 파일 단위 PR로 리뷰를 받습니다. `feat/web`를 통째로 병합하지 않습니다.
- `build_jsonl.py`는 `core/prompt.py`(`build_messages` · `format_target`)와 `core/schema.py`(`check_schema`)를 import합니다. 이 두 파일이 main에 먼저 있어야 동작합니다.

파일럿에서는 train 22건이 198예시(약 9배)가 됐습니다.

| 원본 | 렌더러 | 영업비밀 | H코드 삭제 | EC 추가 | 합계 |
|---:|---:|---:|---:|---:|---:|
| 22 | 104 | 38 | 15 | 19 | 198 |

## 1. 어기면 결과가 무효가 되는 것

- **분할 먼저, 문서 단위로 합니다.** 같은 문서의 변형이 train과 val에 나뉘면 안 됩니다. 분할(`split-frozen`)이 끝난 뒤에 증강합니다.
- **split마다 허용 범위가 다릅니다.**

  | split | 허용 |
  |---|---|
  | train | 렌더러 + 내용 변형 모두 |
  | val | 렌더러만(변형 안정성 점검용). 내용 변형은 넣지 않음 — val은 실제 분포를 봐야 함 |
  | test | 증강 금지. test는 저장소에 없고 개발 쪽이 다루지 않음 |

- **무엇을 보강할지는 새 train 라벨로 다시 정합니다.**
  - 파일럿 프리셋의 보강 근거에는 test 정보가 섞여 있었습니다. "train에 영업비밀 2건 · H코드 없음 2건, test는 9건 · 4건", "test에도 EC 문서가 있음"이라는 판단입니다.
  - 재시작에서는 test 담당이 알려 주는 서식별 건수도 보강 판단에 쓰지 않습니다.
- **val 오류를 보고 val 문서의 표기를 흉내 낸 변형을 만들지 않습니다.** 그러면 val이 조건 선택 근거가 되지 못합니다.
- **학습 예시는 `core/prompt.py`의 `build_messages` · `format_target`으로만 만듭니다.** 추론 입력과 한 글자라도 다르면 안 됩니다.
- **금지 사항**(plan 3.4): 성분 추가 · 삭제, 분류 · 신호어 · H코드 변경, 함유량 수치 변경.
  - 예외는 3절의 내용 변형처럼 **라벨 규칙대로 텍스트와 라벨이 같이 바뀌는 경우**뿐입니다.

## 2. 렌더러 5종 (라벨은 그대로, 겉모양만)

| 렌더러 | 하는 일 | 유의점 |
|---|---|---|
| `bullet` | 줄 앞 기호를 하나로 통일 | 줄 머리 `-`도 기호로 봅니다. 파일럿 train · val에서 `- 006(N)`(제품명 줄), `- 17 : 알레르기성…`(깨진 H코드 줄)이 바뀌는 것을 확인했습니다. 값은 남아서 통과하지만, 규칙을 고치면 값 앞 기호를 건드리지 않는지 다시 확인합니다. 기호가 없는 문서는 원본과 같아 거부됩니다(파일럿 22건 중 5건) |
| `section` | 1~3항 제목의 번호 표기만 바꿈 | 제목 글자는 유지합니다. 스타일은 실제 서식에 있는 것만 씁니다(예: 수입품의 `SECTION 1.`) |
| `subnum` | 가. 나. ↔ 1) (1) 전환 | `3. `처럼 "숫자 + 점"은 일부러 뺐습니다. "3. 공급사 정보"가 3항 제목처럼 보이기 때문입니다. 스타일을 추가할 때도 항 제목과 헷갈리는 모양은 금지입니다. 숫자는 한글 라벨 앞 + 14 이하일 때만 바꿔, 함유량 "1) 30~40"을 건드리지 않습니다 |
| `colon` | 한글이나 `)` 뒤의 콜론 표기를 바꿈 | ` - ` 스타일은 함유량 범위 구분자와 모양이 같습니다(`함유량(%) - 10-20`). 값은 그대로지만 라벨과 값의 경계가 흐려지니 비율을 보고 판단합니다. 값 안에 콜론이 있으면 값이 바뀌어 검사기가 거부합니다(정상 동작) |
| `pagehdr` | 항 제목 앞에 머리글 · 쪽번호 줄을 끼움 | 끼우는 위치가 항 제목 앞뿐이라, 실제로 위험한 "성분표 중간 쪽 넘김"은 만들지 못합니다. 잡음 문구에는 CAS 모양 숫자, H코드, 위험 · 경고, 영업비밀, 회사 · 제품명 같은 **답 후보 문자열**을 넣지 않습니다 |

- 렌더러는 한 번에 하나만 적용합니다(난수 조합 없음).
- 결과가 원본이나 다른 변형과 같으면 최대 6번 다시 뽑고, 그래도 같으면 거부합니다.

## 3. 내용 변형 3종 (텍스트와 라벨을 함께 바꿈, train만)

| 변형 | 하는 일 | 유의점 |
|---|---|---|
| `secret` | CAS(+붙은 KE)를 "영업비밀 · 비공개 · 자료없음(영업비밀) · Trade Secret"으로 가림. 라벨은 `cas_number` · `ke_number` null, `is_substitute_data` true | 가림 표기는 plan 2절 영업비밀 행이 인정하는 것만 씁니다. 텍스트에 한 번만 나오는 CAS만 고릅니다. 성분명은 남기므로, 이름까지 대체명칭인 실제 사례는 배우지 못합니다. 문서당 2개라 파일럿에서 전체의 19%(38/198)였습니다. 비율을 `--dry-run`으로 확인해 기록합니다 |
| `nohcode` | H코드를 모두 지우고 `code`를 모두 null로 | 전부 지우거나 전혀 안 지우거나 둘 중 하나라, 일부 문구만 코드가 없는 문서는 만들지 못합니다. 현행 서식에서 코드만 뺀 모양이라 실제 구서식과는 다릅니다. 텍스트에 코드가 하나라도 남으면 거부합니다(라벨과 모순되는 신호 방지) |
| `ecnum` | CAS 뒤에 체크디짓이 맞는 가짜 EC 번호 칸을 끼움. 라벨은 그대로 | "EC · REACH 번호는 어디에도 담지 않는다"는 라벨 규칙(plan 2절)이 먼저 있어야 합니다. 필요한지는 새 train에서 EC 표기 문서가 부족한지로 다시 판단합니다 |

## 4. 검사기의 빈틈 — 프리셋을 늘리기 전에 먼저 고칠 것

`check_forbidden.check()`는 원문에 있던 정답 값이 변형 뒤에도 남아 있는지 봅니다(공백을 모두 빼고 비교).

| 보는 값 | 보지 않는 값 |
|---|---|
| 제품명 · 권고 용도 · 사용 제한, 성분명 · CAS · KE, 함유량의 숫자, 분류명(`hazard_class`), H코드 · 문구 | 신호어, 분류의 `category`(구분 N), `source_status` · `list_status`, 함유량의 부등호 · "이상/미만", 공급자 |

- **"위 험", "구분2"처럼 오른쪽 값을 건드리는 렌더러는** 검사기부터 넓힌 뒤에 넣습니다.
- **`67 - 64 - 1`처럼 값의 모양을 바꾸는 증강은** 그 정규화(공백 제거 등)가 라벨 규칙에 먼저 있어야 합니다. 검사기는 공백을 빼고 비교하므로 이런 변형을 그냥 통과시킵니다.
- 검사기를 고치면 회귀 테스트도 같이 고칩니다.

## 5. 만든 뒤 확인하고 기록할 것

- **거부 목록:** `python3 pipeline/build_jsonl.py --dry-run`으로 예시 수, 유형별 수, 거부 목록을 봅니다. 거부된 것은 조용히 넘기지 않습니다.
- **길이:** `pagehdr` · `ecnum`은 입력을 늘립니다. 증강 뒤 길이를 다시 재고(파일럿 최대 3,828토큰, 한도 4096), 넘는 예시는 목록으로 남깁니다.
- **배수와 step:** 배수를 바꾸면 step 수도 바뀝니다. 파일럿 r2는 두 가지가 함께 바뀌어 원인을 분리하지 못했습니다. 바꾼 조건과 step 변화를 함께 기록합니다.
- **val.jsonl 고정:** split마다 난수를 따로 써서, train 옵션을 바꿔도 `val.jsonl`은 한 글자도 바뀌지 않게 돼 있습니다. r1 · r2의 val loss를 비교하려면 이 성질을 유지합니다.
- **재현:** seed와 JSONL 해시를 `runs/{날짜}_{r1|r2}/config.json`에 남깁니다.

## 6. 프리셋에 없는 것 (착수 회의에서 넣을지 결정)

plan 3.4 증강표 중 아래 항목은 파일럿 프리셋에 구현돼 있지 않습니다.
- 라벨 표기 변형(CAS No. / CAS 번호 / CAS Registry No.)
- 값의 공백 · 구두점(`67 - 64 - 1`, `위 험`) — 4절대로 라벨 규칙과 검사기가 먼저 필요함
- 레이아웃(표 / 서술형 / 키-값)
- 표 열 쏟음 · 라벨과 값 분리

```
- [ ] 값 모양을 바꾸는 변형이면 라벨 규칙에 그 정규화가 있는가
- [ ] --dry-run으로 유형별 수 · 비율 · 거부 목록을 확인했는가
- [ ] 증강 뒤 길이를 재고, 4096을 넘는 예시를 목록으로 남겼는가
- [ ] val.jsonl이 이전 실행과 같은가 (train 옵션만 바꾼 경우)
- [ ] seed · JSONL 해시 · 예시 수 · step 수를 runs/ config에 기록했는가
```
