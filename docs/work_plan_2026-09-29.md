## r2: 데이터 보강을 하는 경우

가설 제안: **train에 근거가 있는 필드·행 구분 사례의 비중을 바꾸면, r1의 GHS·성분 추출 개선을 유지하면서 추가 오류를 줄일 수 있다.**

1. 원본 train 35건에서 근거를 찾는다. val의 제품 코드·표 구조·정답을 그대로 복제하지 않는다. train에 근거가 없는 유형은 오늘 억지로 만들지 않는다.
2. 오전에 근거가 가장 충분한 보강 유형 **하나**를 선택한다. 제품명·성분 행·상태 구분 세 가지를 모두 동시에 새로 만들지 않는다.
3. 정답이 달라지는 합성은 원문도 함께 바꾸고 두 사람이 전부 검수해야 한다. 스키마 통과만으로 의미가 올바르다고 판단하지 않는다. 기존 원본 라벨은 덮어쓰지 않는다.
4. 원본 35개는 모두 유지하고, 기존 겉모양 변형 일부를 검수된 보강 예시로 교체하는 구성을 우선 검토한다. 예시 수 282·2 epoch·70 step을 유지하면 학습량 차이를 줄일 수 있다. 문서별 반복 수와 총 토큰 수도 비교하며, 고정 step만으로 학습량이 완전히 같아지는 것은 아니다.
5. 별도 train JSONL과 build report를 만들고 r2 설정에서 참조한다. val은 r1과 바이트 단위로 동일하게 유지한다. 기존 보고서 해시를 수동으로 바꿔 검사를 통과시키지 않는다.
6. 모델·학습률 2e-4·rank·alpha·seed·프롬프트·채점기는 유지한다. 데이터 구성 변경을 유일한 실험 변수로 기록한다. 현재 plan.md의 단순 증강 배수 변경보다 넓은 변경임을 명시한다.

11:30까지 이 조건을 충족하지 못하면, **원래 데이터 그대로 학습률만 1e-4로 낮추는 r2**로 전환할지 PM이 결정한다. 이것은 별도 대안이며 데이터 보강과 동시에 적용하지 않는다. 준비되지 않으면 r2 자체를 다음 날로 미룬다.

기존 r2 채택 기준(파싱률·핵심 필드 모두 r1 이상)을 유지한다. 확장 완전 정답, 스키마, 오입력, 문서별 승·패·무를 함께 보고한다. val의 1건 차이만으로 일반화 우위를 선언하지 않는다.

### 순서와 실험 구분

1. 오늘은 후보 하나만 선택한다. 다운로드 전 여유 저장공간을 확인하고 모델·토크나이저 리비전을 고정한다.
2. train 샘플로 chat template·정답 마스킹·출력 종료·길이·메모리를 확인한다. 기존 4B 어댑터를 새 모델에 붙이지 않는다.
3. 기존과 같은 원문·라벨·스키마·프롬프트 내용·few-shot 예시·디코딩 정책으로 새 모델 zero-shot/few-shot을 평가한다. 모델별 공식 chat template 차이와 토큰 길이는 기록한다. 기존 결과는 덮어쓰지 않는다.
4. QLoRA 효과를 보려면 **새 모델 자체의 zero-shot·few-shot·QLoRA** 세 조건이 필요하다. 기존 모델과의 가로 비교는 별도로 낸다.
5. 학습 데이터는 비교하려는 기존 조건과 같게 두고, 실제 tokenizer/template으로 JSONL과 길이 보고서를 새로 검증한다. 기존 모델 설정과 코드가 그대로 호환된다고 가정하지 않는다. 비교 step·LoRA 설정·생성 한도는 결과를 보기 전에 정한다.
6. 결과 폴더는 모델별 별도 out-root, 실행 조건명은 지원되는 이름을 사용한다. scores.csv가 condition/split/subset/metric 기준으로 갱신되므로 **대체 모델 결과가 기존 점수를 덮어쓰지 않도록 모델별 점수 파일 지원 또는 별도 실행 사본을 먼저 준비**한다.
7. 기존 r1+r2 뒤의 추가 학습은 학습 2회 상한을 넘는다. 후보 1종·추가 학습 1회라는 확장 예산과 목적을 먼저 기록한다. 오늘 17:30 이후 새 학습을 급하게 시작하는 것은 기본 일정에 넣지 않는다.
8. 새 모델이 Base에서 이미 우수하면 모델 선택 결과로 보고한다. QLoRA 전후 개선이 없는데 이를 QLoRA 성과로 포장하지 않는다. 여러 모델을 val에서 선택했다면 그 탐색 이력도 보고한다.

## 제품 개발 최소 범위와 작업 충돌 방지

- 오늘 필수 시연: 저장된 실제 val 결과 → 문서 목록·원문·Rule Engine 검토 → 확정 저장 → JSON 다운로드. 재생 결과임을 화면에 표시하고 라이브 추론으로 설명하지 않는다.
- GPU 슬롯이 확보되고 API가 준비되면 train/val PDF 1건으로 업로드→실제 추론→검토 흐름을 추가한다. 미완성이면 저장 결과 시연으로 범위를 줄이고 미구현 항목을 명시한다.
- GPU는 양세윤이 예약·실행을 관리한다. 학습 폴더는 실행 동안 고정하고 코드 수정은 별도 clone/worktree에서 한다. 실험 속도를 잴 때 API 서버 추론을 함께 돌리지 않는다.
- 김건하: 데이터·Rule Engine, 양세윤: 학습·평가·API, 어채은: web·일정·보고 문서를 중심으로 분리한다. 공통 파일은 담당자끼리 먼저 조율한다.
- 정답 수정·출력 정규화·별칭표 변경을 r2 개선과 섞지 않는다. 별도 오류 수정이 필요하면 모든 비교군 재채점 여부와 영향을 기록한다.
- 모델 고정·test 평가를 오늘 일정의 자동 다음 단계로 넣지 않는다. 외부 test 담당·봉인 도구·평가 준비 여부를 별도로 확인한 뒤 진행한다.
