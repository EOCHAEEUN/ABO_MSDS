## 1. 정답 값 오류 — 분류 표기 · 깨진 H코드 · 두 문서 값 뒤바뀜

- **증상:** train 정답 검토 중 원문과 다른 값이 나왔다.
  - 12건에서 `category`가 `구분 N` 형식이 아니었다.
  - KR-HANIL-003: 원문에 H코드가 깨져 인쇄된 문구("H317"이 "17"로)의 `code`가 `"17"`로 들어가 있었다.
  - KR-OCI-003 · KR-OCI-004: 두 문서의 함유량과 급성 독성-경피 분류 · H312 행이 서로 바뀌어 있었다(같은 물질의 다른 농도 제품).
- **원인:** 비슷한 문서를 연달아 라벨링하면서 값을 옮겨 적은 실수, 깨진 코드를 원문 글자 그대로 옮긴 것.
- **처리:** 원문 대조로 수정. 깨진 코드는 추정하지 않고 `null`(plan 2절 "H코드 없이 문구만" 규칙). 변경 목록은 `docs/labels_modified.md`. — `81e25d4`
- **재발 방지:** 같은 제조사 · 같은 물질의 다른 제품은 함께 대조한다. 수정은 CLAUDE.md의 정답 수정 순서(JSON → `validate_labels.py` → 이유 한 줄 → `fix(label):` 커밋)를 따른다.

## 2. 라벨링 규칙 문장과 실제 라벨 불일치

- **증상:** `data/labeling_rules.md`의 흡입 노출매체 규칙이 이미 만든 라벨(KR-NOROO-002 · 005)과 달랐다.
- **원인:** 규칙 파일이 라벨 작성 뒤에 정리됐다.
- **처리:** 라벨은 그대로 두고 규칙 문장을 라벨 방식에 맞췄다(PR #24, `119f008`). 확인에 시간이 걸려 `label-rules-frozen` 태그가 `split-frozen`보다 늦게 달렸다(decisions.md).
- **재발 방지:** 규칙 문장을 먼저 동결하고 라벨링한다. 규칙을 바꾸면 이미 만든 모든 정답에 다시 적용한다(plan 2절).

## 5. `max_new_tokens` 1024에서 JSON이 잘림

- **증상:** 환경 점검 중 fixture 문서(KR-HENKEL-001, 입력 2,141토큰)의 출력이 1024토큰에서 잘려 JSON 파싱 실패.
- **원인:** 임시 기본값이 너무 작았다. 옛 라벨 기준 정답 최장 975토큰 × 1.3 ≈ 1,268에도 못 미쳤다.
- **처리:** 임시 기본값을 2048로 올림(`cbaff66`). 학습 `max_length`(4096)는 쓰지 않았다. 그 값은 입력+정답 합계 상한이고, EOS 없이 도는 실패 사례가 4096까지 채우면 생성 시간이 크게 늘기 때문이다.
- **남은 일:** 실험 고정(단계 7) 전에 새 라벨의 train · val 정답 최장 토큰 × 1.3으로 정해 `eval/experiment.json`에 적는다. 그 전까지 결과는 `n_hit_max_new_tokens`를 함께 본다(현재 val 3개 조건 모두 0).

## 15. 확인 필요: 학습 최대 메모리 · 기기 차이 · 생성 시간 비교

- **최대 메모리:** r1(`runs/0928_r1/config.json`)의 최대 reserved가 8.83 GiB로, 기록된 GPU 메모리 7.96 GiB보다 크다. 이 값이 `--memcheck` 기준(95%)이었다면 실패다. WSL2에서 공유 메모리로 넘어갔을 가능성이 있으나 확인하지 않았다. r2 전에 `--memcheck`로 확인하고, step당 시간(r1 42.6초)을 함께 본다.
- **기기 차이:** 환경 점검(`report/env_check.md`)은 RTX 4060 Laptop, r1 학습은 RTX 5070 Laptop에서 했다. 생성 시간 · 학습 시간은 같은 기기 · 같은 실행 묶음 안에서만 비교한다(재평가 전후 base_zs 평균 생성 시간 29.6초 → 20.3초도 직접 비교하지 않는다).
- **마지막 묶음 버림:** train 282예시 ÷ accum 8이라 epoch마다 마이크로배치 2개가 optimizer step에 들어가지 않는다(`tail_microbatches_dropped_per_epoch: 2`). r2에서 예시 수를 바꾸면 이 값도 함께 기록한다.

## 공통 교훈

- **값을 바꾸는 수정과 실험을 섞지 않는다.** 정답 수정 · 별칭표 변경 · 출력 정규화는 r2 개선과 별도 PR로 하고, 모든 비교군 재채점 여부를 기록한다.
- **실행마다 무엇으로 돌렸는지 남긴다.** 모델 스냅샷, 입력 해시, 학습셋 해시, 기기. 기록이 없으면 결과 차이의 원인을 가를 수 없다(6번).
- **검사 통과 ≠ 정답.** 스키마 · Rule Engine 통과는 형식 확인일 뿐이다(11 · 12번).
- **test 경로는 코드로 막는다.** 규약만으로는 실수를 막지 못한다(9 · 13번).
- **브랜치 정리 때 작업 중인 브랜치는 병합됐어도 지우지 않는다.** 확실하지 않으면 담당자에게 먼저 묻는다.
